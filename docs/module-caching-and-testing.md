# Caching and testing a module

This guide continues the links module of [Writing a module](writing-a-module.md). It explains how the site's output cache keeps the pages a module renders and learns of its changes, and how to test a module with a whole site, on the databases and for the admin's translations.

## The output cache

The site keeps the pages it renders for visitors in memory and serves them again without rendering them, for 60 seconds and up to 32 MB unless **Site settings › Performance** or `Config.OutputCacheTTL` says otherwise; `Config.Development` and `Config.ReloadTemplates` turn it off unless `OutputCacheTTL` is set. See [Deployment](deployment.md#the-output-cache). A module's public handler, template functions and components therefore do not run for every view of a page. The cache keeps a whole page and an HTMX navigation of the same address side by side, up to four lists of request headers that the answers of one address vary on (go-router's `CacheOptions.MaxVarySets`), and many requests at once for a page it does not have render it once per variant. `/metrics` shows its hits, misses, skips, evictions, entries and bytes to requests with `Config.MetricsToken`; see [Deployment](deployment.md#metrics-and-tracing).

Changes made by the site's own process show at once. The app renders the pages again after every successful post to a module's admin sections or to the trash, and after scheduled publication. A visitor's post to the visitor actions below `/_/` or to a page counts only when it succeeded, with a status below 400, and did not say it changed nothing. Spam, a post with mistakes and a post over the throttle say so on their own: `frontend.IsSpam` when it reports true, `KeepForm` and the throttle over its limit call `frontend.NothingChanged(r)`. A module calls it itself for its other answers that store nothing a page shows, as the bundled modules do: comments when they are closed, polls for every result but `voted`, submissions for a body it cannot read, registrations when sign-up is closed, and the newsletter for a signup and a one-click unsubscribe, since no page shows subscribers. A post counts as a change unless it says otherwise, so a module that forgets to mark a post that changed nothing only costs the pages a render, never a page that is out of date. The app gives every visitor's post the record that `NothingChanged` sets with `frontend.TrackChanges(r)`, and reads it with `frontend.Changed(r)`: true unless `NothingChanged` was called. A test of a handler does the same to check what it says; without `TrackChanges`, `NothingChanged` does nothing and `Changed` reports true.

Changes made from Go show at once too, when the module tells the app. A store whose `content.Spec` has `Changed` set to `env.Changed` in `Setup`, as in [Module and Setup](writing-a-module.md#module-and-setup), tells it after every committed write that visitors see, also one made from Go, such as an import through `Store()`, a seed or a background job. For other writes, such as to a table of the module's own, the module calls `env.Changed()` after the commit. `db.AfterCommit(ctx, fn)` calls `fn` at once outside a transaction, and inside one (`DB.Tx`) after the outermost transaction commits; after a rollback it never calls it. `db.AfterWrite(ctx, err, env.Changed)` does the same when `err` is nil and returns `err`, for the last line of a write method, as the bundled services do. A call before the commit is too early: a page rendered in between is kept with the content before the write. `App.Changed()` does the same for the site's own code. A change the app is not told about, a change made by another process and what changes with time alone, such as an event that has passed, show once the pages' time in the cache has passed.

The cache leaves alone the requests of the admin, the visitor actions, the media library and the assets, requests with the editors' session cookie or a kept post (`frontend.KeptFormCookie`), previews and searches with a query. Those two are the only cookies that keep a request from the cache: a request with any other cookie, such as a site's analytics or a theme choice, gets the page the cache keeps for everyone, unless the cookie is registered as personal, as below. The admin's flash messages have a cookie of the admin's path, which site pages never get. The cache never keeps an answer with another status than 200, with `Cache-Control: private` or `no-store`, or that sets a cookie. A page that is the visitor's own altogether, such as a registration looked up by its code, says so with `Cache-Control: private, no-store`. A page that only shows a part differently to a visitor by a cookie of the module or of the site, such as the polls a visitor voted on, registers that cookie in `Setup` with `env.PersonalCookie(name)`: the cache then keeps the page apart for every value of the cookie, also when the answer varies on the `Cookie` header, where other cookies, such as a site's analytics, count for nothing. The polls module registers its cookie, `wt_poll`, this way.

## Testing

`sitetest` starts a whole site on SQLite in a test, in English and Dutch, signed in as administrator, and drives the admin like a browser:

```go
func TestLinks(t *testing.T) {
    s := sitetest.StartWith(t,
        sitetest.Options{Templates: "testdata/templates"},
        links.Module("partners", "Partners"),
    )

    link := s.Submit(s.App.AdminURL("admin.partners.new", url.Values{"locale": {"en"}}), url.Values{
        "Title": {"The Go website"},
        "URL":   {"https://go.dev"},
    })
    s.Publish(link + "?locale=en")
    s.Mount("partners", "Partners", "partners")

    s.Expect("/en/partners", http.StatusOK, `<a href="https://go.dev">The Go website</a>`)
}
```

`s.App.AdminURL(name, args...)` builds admin addresses by route name, as `env.AdminURL` does, so a test does not depend on where the admin is. `testdata/templates/links/list.gohtml` is the screen for the test; sitetest brings the layout. With `Options.StartingPoints`, such as `[]string{"partners"}`, the test uses the starting points that `App.WriteTemplates` generates for those instances instead, and needs no templates of its own. `s.Mount` returns the editor of the page it made, and `s.MountIn(module, translations...)` places a module on a page in several languages, each a `sitetest.Translation` with a locale, title and slug. `s.DraftPage(title, draft, slug)` gives the page titled `title` an unpublished English title and slug. `sitetest.PNG(t, width, height)` makes an image and `s.Upload(name, data)` adds it to the media library. `s.PostFiles(formPage, action, values, files...)` sends a form with a file input from its page, each file a `sitetest.File`, and returns the status and body, for an import. `s.Visitor()` is a browser that is not signed in, `s.Send` posts a visitor's form, `s.Mail` holds the e-mail the site sent and `s.Mails(n)` waits until it has sent `n`, for mail sent in the background, and `sitetest.HasToast(body, level, text)` checks an admin page's messages. `Options.NoAccount` starts a site without accounts, as a fresh install. Sites in tests have the output cache off, so a page shows a change made from Go at once, also one the app is not told about. `Options.OutputCache` keeps the cache on, as the site setting says, for a test of the cache, and `Options.Configure` can set `Config.OutputCacheTTL` itself. Sites in tests hash passwords at the cheapest cost, so they start quickly.

The dashboard's panels load after the page, so `s.Get(s.App.AdminURL("admin.dashboard"))` shows only their placeholders. `s.Dashboard()` returns the dashboard with its panels loaded, and `s.Fragment(path, id)` the part of a page with that ID, as HTMX asks for it. `s.Request(req)` sends a request of your own with the browser's cookies and returns the response unread, for a stream.

`dbtest.Each(t, func(t *testing.T, database *db.DB) { … })` runs a test on SQLite, and on PostgreSQL and MySQL when `WT_TEST_POSTGRES` and `WT_TEST_MYSQL` hold a server's DSN. Apply `media.Schema()` before the module's schema there, since saving content records the media it uses; [`../modules/testimonials/store_test.go`](../modules/testimonials/store_test.go) shows how.

`catalogtest.Complete(t, files, linkInput{})`, of package `sitetest/catalogtest`, fails a test for every text of the section's forms that the admin's catalogues miss in one of the languages the admin comes with (`catalogtest.Languages`): the admin's own `translations/<language>.po` with the module's in `files` on top, as the admin loads them. An empty translation counts as missing, so a label added to a form cannot go untranslated. It skips English (`en_US`, `catalogtest.Source`), the language the texts are written in, since a text its catalogue lacks shows as written; it checks Dutch (`nl_NL`). A module therefore needs a `translations/nl_NL.po`, and a `translations/en_US.po` is optional. The bundled modules check their catalogues this way, such as [`../modules/lists/catalogue_test.go`](../modules/lists/catalogue_test.go).
